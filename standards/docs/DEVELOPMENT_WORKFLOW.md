# 開発ワークフロー — {{PROJECT_NAME}}

> 初回セットアップ(ponytail プラグイン導入・外部ツール連携 hooks)は `docs/SETUP.md` を参照。
> 本書は日常運用の規則を扱う。

## 基本フロー
1. **Issue 起票**(テンプレ必須。Issue 無しの作業着手は禁止)
2. **ブランチ作成**(`start-task` スキル)
3. **調査・再利用検討**(既存実装 / ライブラリ優先)。適用するのは**未知の仕様・新規依存の導入・方式選定のとき**。既知の局所修正に広範な外部探索は求めない。
4. **変更リスクに応じた検証**(コード変更は TDD: RED→GREEN→REFACTOR、カバレッジ 80%+。**文書のみの変更にテスト作成は要求しない**)
5. **PR 作成**(`finish-task` スキル)
6. **独立 QA によるコードレビュー + 受入検証**(`qa-engineer`。CRITICAL/HIGH はマージ前修正必須。指摘の再確認は同じ QA が行う)
7. **マージ** → 8. **Issue クローズ**

## Agent オーケストレーション(PM 主導体制)
> **原則(厳守): PM はコードを直接編集してはならない。**
> すべての実装コードは `.claude/agents/` の各エンジニア Agent へ委任する。
> PM 自身が Write/Edit で実装コードを書き換えることは禁止。**例外なし**(軽微な一行修正・緊急対応も委任)。

- PM の作業範囲: 計画・タスク分解・Issue 起票・委任・**QA 報告の確認**・PR 昇格・統制文書維持・デプロイ等オーケストレーション・オーナー連携。
- **コードレビューは独立 QA(`qa-engineer`)が担う**。PM は「検証証拠・未解決事項・統合リスク」の確認に徹し、**同じレビューを無条件に繰り返さない**。
  - PM が確認するもの: QA 報告に対象コミット・実行コマンドと結果・未実施の検証・未解決指摘が揃っているか。複数 Issue にまたがる統合リスク。受入条件の充足。
- 各 Agent のモデル/effort ポリシーは `docs/AGENTS.md` に従う。
- **1 エージェント 1 Issue**。1 つの担当に複数 Issue を掛け持ちさせない。
- **並列数(試行値)**: 既定は「実装 1 + 独立 QA 1」。上限 3。これ以上は衝突とレビュー待ちで実効が落ちる。
- **委任プロンプトに必ず明記する**:
  - **所有ファイル**(その担当が編集してよい範囲)
  - **並行中の他 Issue**(誰が何を触っているか)
  - **マイグレーション採番規則**(先にマージした PR が勝ち。後発はリベースで採番をずらす)
- **完了時に必ずコミット・push・PR 作成まで行う**(作業をローカルに置いたまま終了しない)。
- **受入条件を満たした後の追加改善は別 Issue にする**(同じ PR を膨らませない)。
- 独立タスクは並列で委任。完了ごとに QA が検証し、指摘があれば実装担当へ差戻し。
- セキュリティ要素(認証・入力処理・DB クエリ・外部 API・決済)の変更時はセキュリティ観点レビューを必ず実施。
- オーナーへの確認は「方針判断が必要な場面のみ」。それ以外は継続的に開発を進行する。

## 文脈管理(Compact・新規セッション)

長い作業でコンテキストが肥大化すると、判断の質が落ち利用枠も消費する。次の基準で「継続 / 整理 / 新規起動」を選ぶ。

| 状況 | 扱い |
|---|---|
| 同じ Issue の実装・デバッグ | **継続**。節目で Compact する |
| 同じ PR の修正対応 | **同じ担当を再開**(文脈を引き継ぐ) |
| 独立した別 Issue | **新規起動**(前の Issue の文脈を持ち込まない) |
| QA の開始 | **実装の履歴を引き継がない独立コンテキストで起動** |
| 同じ QA 指摘の修正確認 | **同じ QA を継続**(指摘の文脈を保持) |
| PM の Phase・統合単位の完了 | 作業状態を保存してから**新規起動** |

- **整理の目安(試行値)**: コンテキスト 100k〜150k 付近で整理の要否を判断する。
  **完了直前なら整理せずそのまま完了してよい**(整理自体にコストがかかる)。
- **Compact 指示の例**:
  > 次を保持して要約: 受入条件 / 競合・冪等性・データ整合性に関する制約 / 決定事項と却下した案 / 変更したファイル / 検証済みコミットと結果 / 未解決の QA 指摘 / 次にやる作業。
  > 探索ログ(ファイル一覧・grep 結果)と重複した出力は要約してよい。

### 作業状態の最小記録

`.guardsmith/state/<issue番号>.md` に、**現在の状態として上書き更新**する(日誌ではない。追記していかない)。
`.guardsmith/` は `.gitignore` 済みでコミットされない。

記録する項目:

- Issue 番号 / ブランチ名 / HEAD の SHA / 未コミット変更の有無
- 受入条件と重要な制約
- 決定事項と却下した案(却下理由つき)
- 変更箇所、検証対象のコミットと検証結果
- 未解決の QA 指摘、未実施の検証
- 次にやる作業

> **注意**: Compact も新規起動も**利用枠をリセットしない**。消費を減らすのは「持ち込む文脈を減らすこと」であって、セッションを作り直すこと自体ではない。
> また、毎ターン実施するものではない(節目だけ)。

## 過剰実装の抑制(ponytail)
[ponytail](https://github.com/DietrichGebert/ponytail) プラグイン(MIT)が SessionStart hook でスキルを注入し、
実装判断に**はしご原則**を適用する: **作らない → 再利用 → 標準ライブラリ → 最小実装**。
上の段で解決できるなら下の段に降りない。迷ったら作らない側を選ぶ。

- 既定強度は **full**。変更は環境変数 `PONYTAIL_DEFAULT_MODE`(lite / full / ultra)。
- コマンド: `/ponytail-review`(差分の過剰設計指摘。`finish-task` の品質ゲート前に実行)、`/ponytail-audit`、`/ponytail-debt`。
- 導入手順・トラブルシュートは `docs/SETUP.md`。

**TDD/カバレッジ 80% との両立**: はしごが削るのはプロダクションコードの過剰な抽象化・自作・先回り実装であり、
テストコード・境界での入力検証・セキュリティ実装・アクセシビリティ(a11y)は削減対象外。
「最小実装」とは検証やテストを省くことではなく、要求を満たす最小の設計を選ぶことを指す。
