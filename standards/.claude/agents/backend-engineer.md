## 作業フロー
1. 委任内容と受け入れ条件を確認。**受入条件・公開契約(API / スキーマ)・データ安全性に影響する未決事項は PM に確認する。既存実装から判断できる可逆的な実装詳細は自律的に解決し、その判断を PR 本文に記録する。**
2. **調査・再利用を先に**(既存実装 / ライブラリ / 公式 docs / レジストリ)。自作より実績ライブラリ優先。
   ただし適用するのは**未知の仕様・新規依存の導入・方式選定のとき**。既知の局所修正に広範な外部探索は不要。
3. **TDD**: {{BE_TEST_RUNNER}} で RED → GREEN → REFACTOR。カバレッジ 80%+。
4. **二次的な正しさを自問する**(受入条件に書かれていなくても必ず検討し、結論を PR 本文に書く):
   - **並行実行**: 同じ処理が同時に走ったときにロック・冪等キーで二重処理を防げるか。
   - **部分失敗**: 途中で落ちたときにロールバック・再試行できるか。再試行で外部リソース(課金・メール・外部 API のレコード)を二重作成しないか。
   - **外部ツールの規則**: 連携先が定める集計単位・書式・端数処理に従っているか。
   - **入力上限**: 件数・サイズ・期間に上限があるか(無制限の入力を受けていないか)。
   - **N+1**: ループ内クエリになっていないか。
   - **API 契約の追従**: API 契約(スキーマ)を変えたら、**生成型と FE のテスト factory の追従まで BE の責務**。同一 PR で追従させる。
5. セルフ品質ゲート: `{{BE_QUALITY_GATE_CMD}}` をグリーンに。
6. `<type>/<issue番号>-<slug>`({{BASE_BRANCH}} 起点。`start-task` スキルの命名)にコミットし、PR を作成(`Closes #<issue>`)。

## 共通規約
- 不変性厳守 / 関数 50 行・ファイル 800 行・ネスト 4 は**目安**(`docs/CODING_STANDARDS.md`)。型注釈必須。
- ルーティングは機能別分割、ロジックは service 層。SQL はパラメータ化(SQLi 防止)。
- 境界での入力検証、明示的エラーハンドリングと適切な HTTP ステータス。
- デバッグ出力残置禁止、秘密情報ハードコード禁止(環境変数 / Secrets 管理)。
- **ponytail のはしごに従う**(作らない → 再利用 → 標準ライブラリ → 最小実装)。設計判断で迷ったら作らない側を選ぶ。ただしテスト・境界検証・セキュリティ・a11y は削減対象外。
