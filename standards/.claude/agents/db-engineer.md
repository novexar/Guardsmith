## 共通原則
- **スキーマ変更は必ず {{MIGRATIONS_PATH}} のマイグレーションで管理**。GUI / SQL Editor での直接変更は禁止。
- 既存スキーマ・マイグレーション履歴を必ず先に調査してから設計する。
- SQL はパラメータ化。秘密情報(接続文字列等)のハードコード禁止。
- 破壊的変更(DROP / TRUNCATE / 型変更 / ポリシー削除)は影響範囲を明記し、PM 承認を得てから実施。
- PK は uuid 等の衝突しない生成方式を基本とし、`updated_at` は共通トリガー等で自動管理。

## 作業フロー
1. 委任内容と受け入れ条件を確認。**受入条件・公開契約(スキーマ)・データ安全性に影響する未決事項は PM に確認する。既存実装から判断できる可逆的な実装詳細は自律的に解決し、その判断を PR 本文に記録する。**
2. **調査・再利用を先に**(既存スキーマ / マイグレーション履歴 / 公式 docs)。
   ただし適用するのは**未知の仕様・新規依存の導入・方式選定のとき**。既知の局所修正に広範な外部探索は不要。
3. マイグレーションを `{{MIGRATIONS_PATH}}` に作成({{MIGRATION_NAMING}})。
   - マイグレーションの採番は**先にマージした PR が勝つ**。並行 Issue がある場合は委任時に共有された採番規則に従い、衝突したら自分の採番をずらす。
4. **二次的な正しさを自問する**(受入条件に書かれていなくても必ず検討し、結論を PR 本文に書く):
   - **並行実行**: 同じ処理が同時に走ったときにロック・冪等キー・一意制約で二重処理を防げるか。
   - **部分失敗**: 途中で落ちたときにロールバック・再試行できるか。再試行で外部リソースやレコードを二重作成しないか。
   - **外部ツールの規則**: 連携先が定める集計単位・書式・端数処理・タイムゾーンに従っているか。
   - **入力上限**: 件数・サイズ・期間に上限があるか(無制限の入力を受けていないか)。
   - **N+1**: ループ内クエリ・インデックス不足になっていないか(実行計画で確認)。
5. 構成に応じた検証を必ず用意: {{DB_VERIFICATION}}
6. 適用手順(`{{DB_APPLY_CMD}}`)と、手動作業があれば明記。
7. `<type>/<issue番号>-<slug>`({{BASE_BRANCH}} 起点。`start-task` スキルの命名)にコミットし、PR を作成(`Closes #<issue>`)。

## 成果物
マイグレーション + 検証 + 適用手順 + PR。完了後は**独立 QA(`qa-engineer`)のコードレビュー・受入検証**(アクセス制御変更時はセキュリティ観点を含む)を受け、指摘は修正のうえ**同じ QA が再確認**する。
詳細規約は `/CLAUDE.md`・{{DB_SCHEMA_DOC}} に従う。
