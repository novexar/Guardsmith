# v0.5.0 移行ガイド — 既存プロジェクトの差分適用チェックリスト

[English](v0.5.0.md) | **日本語**

対象: v0.2.1 標準(`<!-- standards: novexar/guardsmith v0.2.1 -->`)で生成・運用中の既存プロジェクト(例: Tenavis)。

> **まず前提**: リモート参照はタグ固定のため、**何もしなくても壊れない**(現行タグのまま動き続ける)。
> v0.5.0 への追随は**任意**であり、以下のチェックリストは**段階適用可**
> (1 と 2 以外は独立。都合の良い項目から順に適用してよい)。

v0.5.0 の変更内容の全体像は [CHANGELOG.ja.md](../../CHANGELOG.ja.md) を参照。

## チェックリスト

### 1. extends タグを v0.5.0 へ上げ、drift を復元する

`guard.policy.yaml` の extends を更新:

```yaml
extends:
  - github:novexar/guardsmith//presets/baseline.yaml@v0.5.0 # ← @v0.2.1 から変更
```

`guard lint` を実行すると、標準 skills(start-task / finish-task 等)のマスター乖離が
`drift/skills-sync` の warn として表面化する。`guard sync` で差分を確認(dry-run)し、
`guard sync --write` でマスター内容へ復元する(`## PJ固有手順` セクションのローカル編集は保全される)。

- [ ] extends のタグを `@v0.5.0` に変更した
- [ ] `guard sync --write` を実行し、`## PJ固有手順` が保全されていることを確認した
- [ ] 確認コマンド: `npx @guardsmith/cli lint`(drift warn が解消していること)

### 2. FE を持つ PJ: frontend プリセットと DESIGN.md

FE を持つ PJ のみ。`extends` に frontend プリセットを追加し、DESIGN.md を配置・具体化する
(詳細: standards/docs/FRONTEND_STANDARDS.md)。BE のみの PJ はこの項をスキップ。

```yaml
extends:
  - github:novexar/guardsmith//presets/baseline.yaml@v0.5.0
  - github:novexar/guardsmith//presets/frontend.yaml@v0.5.0 # ← FE を持つ PJ のみ
```

- [ ] frontend プリセットを extends に追加した
- [ ] `DESIGN.md` をリポジトリルートに配置し、PJ 向けに具体化した(プレースホルダ残置は error)
- [ ] 確認コマンド: `npx @guardsmith/cli lint`(`frontend/design-md` / `frontend/shadcn-config` 等が PASS)

### 3. agents frontmatter に model/effort を追加

各 `.claude/agents/*.md` の frontmatter に model / effort を追記する(ポリシー: docs/AGENTS.md。
目安: qa-engineer は fable + effort high、実装系エンジニアは sonnet)。
日付付き model ID(例: `claude-sonnet-4-20250514`)のハードコードは
baseline の `agents/no-pinned-model` が warn する — エイリアス表記にする。

- [ ] 全 agent に model(必要なら effort)を追記した
- [ ] 確認コマンド: `npx @guardsmith/cli lint`(`agents/no-pinned-model` の warn が出ないこと)

### 4. ponytail(過剰実装抑制)の導入

`.claude/settings.json`(標準マスターのものを `guard sync` で取得、または手動配置)により
ponytail マーケットプレイスがフォルダを開いた時点で自動登録される。

- [ ] `.claude/settings.json` を配置した(手順 1 の sync で配布される)
- [ ] 初回セットアップ: フォルダ trust の確認に応答。プラグインが有効にならない場合は
      `/plugin marketplace add DietrichGebert/ponytail` → `/plugin install ponytail@ponytail`
- [ ] 確認: Claude Code で `/ponytail-review` が実行できること

### 5. Docker ローカル CI の導入

日常 CI を GitHub Actions から Docker ローカルへ移行する。標準マスターの一式
(`docker/ci/`、`docker-compose.ci.yml`、`Makefile`)を導入し、自 PJ のスタックへ具体化する
(詳細: docs/CI_CD.md)。CI 結果 JSON は `.guardsmith/ci-results/` に出力され、外部ツールの受け口になる。

- [ ] `docker/ci/` / `docker-compose.ci.yml` / `Makefile` を配置し、スタックに合わせて具体化した
- [ ] 確認コマンド: `make ci`(全ステップ GREEN、`.guardsmith/ci-results/` に結果 JSON が出力される)

### 6. GitHub Actions をテスト系から deploy のみに

`.github/workflows/` からテスト系ワークフロー(pull_request トリガの lint/test 等)を削除し、
main push の `deploy.yml` のみにする。baseline の `ci/no-remote-test-workflows`(warn)が検出に使える。

- [ ] テスト系ワークフローを削除し、`deploy.yml` のみ残した
- [ ] 確認コマンド: `npx @guardsmith/cli lint`(`ci/no-remote-test-workflows` の warn が消えること)

### 7. Issue テンプレートとブランチ命名の切替

- Issue テンプレートを feature / bug / chore の3種(固定見出し)に差し替える(旧 `task.md` は削除)。
- 作業ブランチ命名を `<type>/<issue番号>-<slug>`(例: `feature/142-preset-loader`)に切り替える。
  既存ブランチのリネームは不要 — **切替日以降に作成する新規ブランチから**適用すればよい。

- [ ] `.github/ISSUE_TEMPLATE/` を feature.md / bug.md / chore.md に差し替えた(task.md 削除)
- [ ] チームに切替日を周知し、新規ブランチから新命名を適用した
- [ ] 確認: `start-task` スキルが新命名でブランチを作成すること

### 8. 外部ツール連携 hooks(任意)

ccdash 等の外部ツールと連携する場合のみ。`.claude/settings.local.json.example` を
`.claude/settings.local.json` にコピーし、受信側 URL・トークン(環境変数名)を編集する。
トークン・URL は `settings.local.json` 側にのみ置き、コミットしない(`.gitignore` 済み)。

- [ ] `.claude/settings.local.json` を作成し、自環境の URL・トークンを設定した
- [ ] 確認: セッション開始時に受信側へ SessionStart イベントが届くこと。
      `npx @guardsmith/cli lint` の `security/no-secrets-in-context` が PASS のままであること

すべて適用後、以下が GREEN であれば移行完了:

```bash
npx @guardsmith/cli lint   # exit 0(drift・プレースホルダ・新ルールの warn なし)
make ci                    # ローカル CI 全ステップ GREEN
```

CLAUDE.md 末尾のスタンプが `<!-- standards: novexar/guardsmith v0.5.0 -->` に
更新されていること(手順 1 の sync 対象外の場合は手動で更新)も確認する。
