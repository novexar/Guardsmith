# v0.7.0 Migration Guide — incremental checklist for existing projects

**English** | [日本語](v0.7.0.ja.md)

Audience: projects operating on the v0.6.0 standards.
If you are migrating from an older version, apply the [v0.5.0](v0.5.0.md),
[v0.5.1](v0.5.1.md), [v0.5.2](v0.5.2.md) and [v0.6.0](v0.6.0.md) guides first, then
continue with this guide.

> **First, the baseline**: remote references are tag-pinned, so **nothing breaks if you do
> nothing**. Catching up is optional.

> **Requires `@guardsmith/cli` 0.6.0 or newer.** The v0.7.0 baseline carries the new
> `drift3` check, and an older CLI rejects it as an unknown check under its strict schema.
> Upgrade the CLI **before** bumping the `extends` tag (step 2).

> **Breaking: `guard sync` now exits 1 when there are conflicts.** Until v0.6.0 the command
> always exited 0. If your CI runs `guard sync` (with or without `--write`), that job will
> now fail as soon as a standards change cannot be applied cleanly. Decide before you bump
> whether that job should block the pipeline or be allowed to fail. `guard lint` exit codes
> are unchanged.

v0.7.0 changes **how a project absorbs a standards update**:

- Until now, catching up meant reading the diff between two master tags and hand-applying
  the standard sections — which is why the v0.6.0 guide had to spell out "copy the standard
  sections of `qa-engineer.md` from the master by hand".
- v0.7.0 turns that into a **three-way merge**. The master at your current tag is the base,
  the master at the new tag is theirs, your repository is ours.
- The merge needs to know which strings you substituted for the template placeholders, so
  projects now keep a committed dictionary at `guardsmith.vars.yaml`.
- `guard bump <tag>` does the whole round in one command: rewrite the `extends` tags, merge
  the files, and move `guardsmith.vars.yaml` and the `CLAUDE.md` stamp to the new tag.

Existing projects have exactly **two** steps.

## Checklist

### 1. Generate and review `guardsmith.vars.yaml`

```
guard sync --init-vars
```

This writes `guardsmith.vars.yaml` at the project root and exits without syncing anything.
It infers each value by lining your files up against the master at your current tag.

```yaml
version: 1
standards: v0.6.0
vars:
  PROJECT_NAME: "BizCore"
  OWNER: "Novexar"
  ORG/REPO: "novexar/bizcore"
  "単一システム | モノレポ": "モノレポ"
  FE_STACK: "React 19 + Vite + TailwindCSS v4"
```

Keys are the text **inside** the `{{ }}` token, verbatim — including slashes (`ORG/REPO`)
and choice tokens (`"単一システム | モノレポ"`). `standards` is the tag the project was
generated from; `--init-vars` reads it from the `CLAUDE.md` trailing stamp.

> **Review the generated file.** Inference is a best effort, and a wrong value means
> `guard bump` will silently rewrite your wording later.
>
> - Keys it could not determine are set to `TODO`. **While any `TODO` remains — or while
>   any placeholder used by the standards is missing from `vars` — both `guard bump` and
>   `guard sync --write` stop with exit code 2.** A dry-run and `guard lint` still work and
>   name the keys that are missing; only writing is refused, because an unfilled value would
>   otherwise be written into the project verbatim.
> - Keys with several candidates get the most frequent one, with all candidates listed in a
>   comment next to the key. Pick the right one and delete the comment.
> - Values that match a secret pattern are dropped to `TODO` on purpose — this file is
>   committed. Never put a token, API key, password or connection string in it.
> - If `CLAUDE.md` has no trailing stamp, `--init-vars` cannot tell which tag you are on and
>   exits with code 2. Write `standards:` by hand and run it again.
> - If `guardsmith.vars.yaml` already exists, `--init-vars` does **not** overwrite it and
>   exits with code 2.

Projects created with `guard new` at v0.7.0 or later already have this file and can skip
this step.

- [ ] `guardsmith.vars.yaml` generated
- [ ] Every `TODO` resolved
- [ ] Every ambiguous candidate comment reviewed and removed
- [ ] No secrets in the file
- [ ] `standards` matches the tag in the `CLAUDE.md` trailing stamp
- [ ] File committed

### 2. Dry-run, then bump

```
guard sync          # dry-run: prints the plan and the predicted conflicts, writes nothing
guard bump v0.7.0   # applies it, and moves the extends tags and guardsmith.vars.yaml
```

Always run the dry-run first. `guard sync` without `--write` never touches a file; it exits
0 when everything applies cleanly and 1 when at least one file conflicts.

`guard bump v0.7.0` rewrites the `github:novexar/guardsmith...@vX.Y.Z` references in
`guard.policy.yaml` (baseline, frontend, and any `drift3` source you wrote yourself), merges
the files, **also runs the section-level sync for `.claude/skills/**` against the master at
the new tag**, then sets `guardsmith.vars.yaml`'s `standards` and the `CLAUDE.md` stamp to
the new tag. One command covers the same ground as `guard sync --write`, so there is no
separate step to forget. Use `--repo <owner>/<repo>` if your standards live somewhere other
than `novexar/guardsmith`.

> **Only one standards repository is followed.** `guardsmith.vars.yaml` records a single
> `standards` tag, so the tag can only belong to one source. `drift3` rules pointing at any
> other repository — a Layer 2 overlay such as
> `github:novexar/guardsmith-private//standards@v3.0.0` — are **not** bumped and not
> compared against your tag; they are reported with a warning and left to their own pinned
> tag. For the same reason a policy may carry **at most one** `drift3` rule for the target
> repository; a second one is a policy error (exit 2).

**If anything conflicts, `guard bump` writes nothing at all** — not the policy, not the
files, not the vars, and not the skills — lists the conflicting files and exits 1. Resolve
**only the listed files**, then run `guard sync --write` to apply the rest. Pass
`--conflict-markers` if you want the conflicting files written out with `<<<<<<<` /
`|||||||` / `=======` / `>>>>>>>` markers instead; the exit code is still 1.

`guard sync --write` behaves the same way: it builds the 3-way plan first, and a conflict
suppresses the section-level restore too, so a half-applied tree never happens. Every file
either command writes — the merged files, the section restores, `guardsmith.vars.yaml` and
the `CLAUDE.md` stamp — goes out as a **single batch**: all of them are staged first, and if
committing any one of them fails the ones already committed are restored. There is no state
in which half the files carry the new tag.

| Command            | Exit 0                        | Exit 1                                | Exit 2                                                          |
| ------------------ | ----------------------------- | ------------------------------------- | --------------------------------------------------------------- |
| `guard sync`       | no conflicts (dry-run or not) | conflicts                             | run-time error, an incomplete vars on `--write`, or a roll-back |
| `guard bump <tag>` | applied                       | conflicts (policy and vars unchanged) | run-time error, an incomplete vars, or a roll-back              |

> **The project is never rolled back silently.** If `guardsmith.vars.yaml` is at a _newer_
> tag than the policy distributes — which happens when a bump's policy write failed, or the
> policy was reverted or hand-edited — a plain three-way would run "new → old" and undo the
> standards. `guard sync` and `guard bump` refuse with exit 2 and print no plan, and
> `guard lint` reports it as a `warn`. Fix the `extends` tag, or re-run
> `guard bump <the newer tag>`; pass `--allow-downgrade` only when going back really is
> what you want.

Flags:

```
guard sync  [--root <dir>] [--policy <file>] [--write] [--no-cache] [--no-gitignore]
            [--conflict-markers] [--init-vars] [--allow-downgrade]
guard bump  <tag> [--root <dir>] [--policy <file>] [--repo <owner>/<repo>]
            [--no-cache] [--no-gitignore] [--conflict-markers] [--allow-downgrade]
```

- [ ] Upgraded `@guardsmith/cli` to 0.6.0 or newer (and the Action's `cli-version` /
      `release-tag` if you pin them)
- [ ] Reviewed the `guard sync` dry-run output
- [ ] Ran `guard bump v0.7.0` and resolved any conflicts
- [ ] Verify: `npx @guardsmith/cli lint`
- [ ] Checked that any CI job running `guard sync` handles the new exit code 1
- [ ] If your policy inherits a `drift3` rule for another standards repository, checked the
      warning it now prints (it keeps its own pinned tag and is not bumped)

### 3. What lands automatically, and what becomes a conflict

The merge is per file, and within a file per changed region:

| Situation                                                                                         | Result                                                                                             |
| ------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| A standard section the project never touched, changed in the master                               | Applied automatically                                                                              |
| A section the project rewrote, changed in the master as well                                      | **Conflict** — the file is left untouched and reported                                             |
| A section the project rewrote, unchanged in the master                                            | Your wording is kept                                                                               |
| A file only the new master has (e.g. `docs/SETUP.md`)                                             | Added                                                                                              |
| A file the master dropped                                                                         | **Not deleted.** Reported as `info` — remove it yourself if you agree                              |
| A file the project deleted on purpose (e.g. `backend-engineer.md` in a project without a backend) | Skipped with an `info`. It is not re-created                                                       |
| A file only the project has                                                                       | Never touched                                                                                      |
| A placeholder with no entry in `vars`                                                             | Left as the literal `{{KEY}}` and reported as `info`; **writing is refused** until it is filled in |

Rows you deleted following a `<!-- gen: 採用しない層は行ごと削除 -->` instruction behave the
same way: the deletion is yours and survives, unless the master changed that very row, in
which case you get a conflict and decide by hand.

The `drift3` check reports the same state during `guard lint`:

```
WARN  drift/standards-sync  standards v0.6.0 → v0.7.0 not applied (4 files, applies cleanly) — run: guard bump v0.7.0
INFO  drift/standards-sync  standards v0.6.0 → v0.7.0 needs manual merge (conflicts in .claude/agents/qa-engineer.md)
INFO  drift/standards-sync  guardsmith.vars.yaml not found — falling back to section comparison. run: guard sync --init-vars
INFO  drift/standards-sync  2 placeholder(s) missing from guardsmith.vars.yaml: FE_STACK, DB — guard sync --write and guard bump refuse to run until filled
```

The existing section-level `drift` check (`.claude/skills/**`, `allow_sections`) is
unchanged, and so is `guard sync`'s behaviour for policies that carry no `drift3` rule.

- [ ] Read the dry-run plan and understood which files were reported as conflicts

### 4. If you already applied the v0.6.0 standards by hand

Some projects (for example `cctower`) took the v0.6.0 standard sections in manually rather
than waiting for a sync. That is fine, and it is exactly what a three-way merge is good at:

- Where your hand-applied text **matches the old → new master diff**, the merge sees "ours
  and theirs made the same change" and reports **no conflict** — nothing is applied twice.
- Where it **differs** (you paraphrased, reordered, or only took part of it), you get a
  **conflict** on that file. Compare your version against the master at `v0.7.0` and decide
  which wording to keep.

So a hand-migrated project is not penalised, but expect a handful of conflicts in the files
you edited most.

- [ ] Compared the conflicting files against the master at `v0.7.0`

### 5. Rollback

Both steps are reversible, and nothing outside the repository changes:

1. Revert the `extends` tags in `guard.policy.yaml` to `@v0.6.0`.
2. Revert `standards:` in `guardsmith.vars.yaml` to `v0.6.0` (and the `CLAUDE.md` trailing
   stamp along with it — the two must agree).
3. Revert the merged file changes with git if you want the old content back.

The CLI may stay at 0.6.0 or newer; it reads the v0.6.0 baseline unchanged. Keeping
`guardsmith.vars.yaml` after a rollback is harmless — it is only read when a `drift3` rule
is in effect.

- [ ] Rollback steps shared with the team
