# v0.5.0 Migration Guide — incremental checklist for existing projects

**English** | [日本語](v0.5.0.ja.md)

Audience: existing projects generated and operated on the v0.2.1 standards
(`<!-- standards: novexar/guardsmith v0.2.1 -->`), e.g. Tenavis.

> **First, the baseline**: remote references are tag-pinned, so **nothing breaks if you do
> nothing** (the current tag keeps working). Catching up to v0.5.0 is **optional**, and the
> checklist below can be **applied incrementally** (items other than 1 and 2 are independent;
> apply them in whatever order suits you).

For the full picture of what changed in v0.5.0, see [CHANGELOG.md](../../CHANGELOG.md).

## Checklist

### 1. Bump the extends tag to v0.5.0 and restore drift

Update `extends` in `guard.policy.yaml`:

```yaml
extends:
  - github:novexar/guardsmith//presets/baseline.yaml@v0.5.0 # ← changed from @v0.2.1
```

Running `guard lint` will surface drift of the standard skills (start-task / finish-task,
etc.) from the master as `drift/skills-sync` warnings. Review the diff with `guard sync`
(dry-run), then restore the master content with `guard sync --write` (local edits in the
`## PJ固有手順` section are preserved).

- [ ] Changed the extends tag to `@v0.5.0`
- [ ] Ran `guard sync --write` and confirmed `## PJ固有手順` was preserved
- [ ] Verify: `npx @guardsmith/cli lint` (drift warnings resolved)

### 2. Projects with a frontend: frontend preset and DESIGN.md

Only for projects with a frontend. Add the frontend preset to `extends`, then place and
concretize DESIGN.md (details: standards/docs/FRONTEND_STANDARDS.md). Backend-only projects
skip this item.

```yaml
extends:
  - github:novexar/guardsmith//presets/baseline.yaml@v0.5.0
  - github:novexar/guardsmith//presets/frontend.yaml@v0.5.0 # ← projects with a FE only
```

- [ ] Added the frontend preset to extends
- [ ] Placed `DESIGN.md` at the repository root and concretized it for the project
      (leftover placeholders are an error)
- [ ] Verify: `npx @guardsmith/cli lint` (`frontend/design-md` / `frontend/shadcn-config`
      etc. PASS)

### 3. Add model/effort to agents frontmatter

Add model / effort to the frontmatter of each `.claude/agents/*.md` (policy:
docs/AGENTS.md; rule of thumb: qa-engineer gets fable + effort high, implementation
engineers get sonnet). Hardcoded date-suffixed model IDs
(e.g. `claude-sonnet-4-20250514`) trigger a warn from the baseline's
`agents/no-pinned-model` — use alias notation instead.

- [ ] Added model (and effort where needed) to every agent
- [ ] Verify: `npx @guardsmith/cli lint` (no `agents/no-pinned-model` warnings)

### 4. Introduce ponytail (over-implementation restraint)

With `.claude/settings.json` (fetched from the standards master via `guard sync`, or
placed manually), the ponytail marketplace is registered automatically when the folder is
opened.

- [ ] Placed `.claude/settings.json` (distributed by the sync in step 1)
- [ ] First-time setup: answer the folder-trust prompt. If the plugin does not activate:
      `/plugin marketplace add DietrichGebert/ponytail` → `/plugin install ponytail@ponytail`
- [ ] Verify: `/ponytail-review` runs in Claude Code

### 5. Introduce Docker-based local CI

Move day-to-day CI from GitHub Actions to local Docker. Adopt the full set from the
standards master (`docker/ci/`, `docker-compose.ci.yml`, `Makefile`) and concretize it for
your project's stack (details: docs/CI_CD.md). CI result JSON is written to
`.guardsmith/ci-results/` and serves as the interface for external tools.

- [ ] Placed `docker/ci/` / `docker-compose.ci.yml` / `Makefile` and concretized them for
      the stack
- [ ] Verify: `make ci` (all steps GREEN, result JSON written to `.guardsmith/ci-results/`)

### 6. Reduce GitHub Actions to deploy only

Remove test-oriented workflows (pull_request-triggered lint/test, etc.) from
`.github/workflows/`, leaving only `deploy.yml` for main pushes. The baseline's
`ci/no-remote-test-workflows` (warn) can be used for detection.

- [ ] Removed test-oriented workflows, leaving only `deploy.yml`
- [ ] Verify: `npx @guardsmith/cli lint` (the `ci/no-remote-test-workflows` warning is gone)

### 7. Switch issue templates and branch naming

- Replace the issue templates with the three types feature / bug / chore (fixed headings);
  the old `task.md` is removed.
- Switch working-branch naming to `<type>/<issue number>-<slug>`
  (e.g. `feature/142-preset-loader`). No need to rename existing branches — apply the new
  naming **only to branches created after the cutover date**.

- [ ] Replaced `.github/ISSUE_TEMPLATE/` with feature.md / bug.md / chore.md (task.md removed)
- [ ] Announced the cutover date to the team and applied the new naming from new branches
- [ ] Verify: the `start-task` skill creates branches with the new naming

### 8. External tool hooks (optional)

Only if you integrate with external tools such as ccdash. Copy
`.claude/settings.local.json.example` to `.claude/settings.local.json` and edit the
receiver URL and token (environment variable name). Keep tokens and URLs only in
`settings.local.json` and never commit it (already in `.gitignore`).

- [ ] Created `.claude/settings.local.json` and set your environment's URL and token
- [ ] Verify: the receiver gets a SessionStart event when a session starts, and
      `npx @guardsmith/cli lint` keeps `security/no-secrets-in-context` PASS

## Completion check

After applying everything, the migration is complete when the following are GREEN:

```bash
npx @guardsmith/cli lint   # exit 0 (no drift, placeholder, or new-rule warnings)
make ci                    # all local CI steps GREEN
```

Also confirm that the stamp at the end of CLAUDE.md has been updated to
`<!-- standards: novexar/guardsmith v0.5.0 -->` (update it manually if it was not covered
by the sync in step 1).
