# v0.6.0 Migration Guide — incremental checklist for existing projects

**English** | [日本語](v0.6.0.ja.md)

Audience: projects operating on the v0.5.2 standards.
If you are migrating from an older version, apply the [v0.5.0](v0.5.0.md),
[v0.5.1](v0.5.1.md) and [v0.5.2](v0.5.2.md) guides first, then continue with this guide.

> **First, the baseline**: remote references are tag-pinned, so **nothing breaks if you do
> nothing**. Catching up is optional.

> **Requires `@guardsmith/cli` 0.5.0 or newer.** The v0.6.0 baseline carries the new
> `import-budget` check, and an older CLI rejects it as an unknown check under its strict
> schema. Upgrade the CLI **before** bumping the `extends` tag (step 9).

v0.6.0 reorganizes **who checks quality** and **how much context stays resident**:

- Code review moves from the PM to an **independent QA agent** (`qa-engineer`), which now
  owns both code review and acceptance verification.
- Engineer models follow a new policy (BE/DB on `opus`, FE on `sonnet`, QA on `opus`).
- `@` imports in `CLAUDE.md` are narrowed to the one document that must stay resident.
- Line-count rules (50 / 800 / 4) become **guidelines**, not thresholds.

## Checklist

### 1. Change the `model` in agent frontmatter

| Agent               | Before             | After                                                           |
| ------------------- | ------------------ | --------------------------------------------------------------- |
| `qa-engineer`       | `fable`            | `opus`                                                          |
| `backend-engineer`  | `sonnet`           | `opus`                                                          |
| `db-engineer`       | `sonnet`           | `opus`                                                          |
| `frontend-engineer` | `sonnet`           | `sonnet` (unchanged)                                            |
| PM (main session)   | — (no frontmatter) | Claude Fable 5.1 / High — **the only session on the top model** |

Keep `effort: high` on `qa-engineer`. Do not pin dated model IDs (the
`agents/no-pinned-model` rule checks this). The rationale and the source data are in
`docs/AGENTS.md`.

- [ ] Updated `model` in `.claude/agents/*.md`
- [ ] Confirmed in a subagent's **execution log** which model the alias actually resolved
      to (the frontmatter value alone is not evidence)

### 2. Update the `qa-engineer` responsibilities

`qa-engineer` is now the single independent quality gate: **code review** (concurrency,
idempotency, data integrity, permissions, input bounds, performance, design defects) **and**
acceptance/behaviour verification (acceptance criteria, happy/error paths, integration,
critical user flows, regression, a11y on the frontend). It also carries a
"recurrence-prevention" verification table.

Pull the standard sections in with:

```
guard sync --write
```

`guard sync` overwrites the standard sections only; **project-specific sections are not
overwritten**. Run it without `--write` first (dry-run) and review the diff.

> **Note**: `guard sync` restores exactly the files matched by the `paths` of your policy's
> `drift` rules. The baseline's drift rule covers `.claude/skills/**` only, so
> `.claude/agents/**` is **not** synced out of the box. Either add `.claude/agents/**` to
> the drift `paths` in your own policy, or copy the standard sections of `qa-engineer.md`
> from the master (`standards/.claude/agents/qa-engineer.md` at tag `v0.6.0`) by hand.

- [ ] `.claude/agents/qa-engineer.md` carries the new responsibilities and report format
- [ ] Project-specific sections survived the sync

### 3. Review the `@` references in CLAUDE.md / DEVELOPMENT_WORKFLOW.md (manual)

`@docs/...` is an **import**: the whole file is loaded at every session start and stays
resident. Moving content to `docs/` and referencing it with `@` therefore does **not**
reduce context.

Change these to plain paths with a "when to read it" note:

| Reference                       | After                                                                         |
| ------------------------------- | ----------------------------------------------------------------------------- |
| `@docs/CODING_STANDARDS.md`     | keep as `@` (the only resident document)                                      |
| `@docs/REQUIREMENTS.md`         | `docs/REQUIREMENTS.md` — when filing an issue / checking acceptance criteria  |
| `@docs/ARCHITECTURE.md`         | `docs/ARCHITECTURE.md` — when changing structure or adding a component        |
| `@docs/DEVELOPMENT_WORKFLOW.md` | `docs/DEVELOPMENT_WORKFLOW.md` — when starting work, opening a PR, delegating |
| `@docs/CI_CD.md`                | `docs/CI_CD.md` — when `make ci` fails or CI changes                          |
| `@docs/INFRA.md`                | `docs/INFRA.md` — when infrastructure changes                                 |

Keep `CLAUDE.md` at 120 lines or fewer, but do not treat the line count alone as proof
that the context is light — check the resident volume with `guard lint`. The new
`claude-md/import-budget` rule prints it as an `info`:

```
INFO  claude-md/import-budget CLAUDE.md — resident context: 2 files, 7633 chars (≈1909 tokens, rough estimate)
  - docs/CODING_STANDARDS.md: 5547 chars
  - CLAUDE.md: 2086 chars
```

Over **32,000 characters** the rule reports a `warn`. The token figure is a rough
`chars / 4` estimate, not a measurement.

A package name such as `@scope/pkg` written outside backticks is read as an import by
Claude Code as well, so the rule reports it as `unresolved import`. Wrap those in
backticks — the officially documented way to mention a path without importing it.

- [ ] Only `docs/CODING_STANDARDS.md` remains behind `@` in `CLAUDE.md`
- [ ] Every other document is listed with a plain path plus a "when to read it" condition
- [ ] Checked the `import-budget` info and confirmed the resident volume is under 32,000
      characters
- [ ] Wrapped package names such as `@scope/pkg` in backticks so they stop being read as
      imports

### 4. Add docs/SETUP.md

First-time setup content (ponytail plugin installation, external-tool hooks) moves out of
`docs/DEVELOPMENT_WORKFLOW.md` into a new `docs/SETUP.md` for administrators.
`DEVELOPMENT_WORKFLOW.md` keeps only day-to-day rules and a pointer to `SETUP.md`.

- [ ] `docs/SETUP.md` exists and holds the setup steps
- [ ] `docs/DEVELOPMENT_WORKFLOW.md` no longer duplicates them

### 5. Start using .guardsmith/state/

Record the minimal working state for an issue in `.guardsmith/state/<issue-number>.md`,
**overwriting it as the current state** (it is not a journal). `.guardsmith/` is already
gitignored.

Contents: issue number, branch, HEAD, uncommitted changes, acceptance criteria and key
constraints, decisions and rejected alternatives, changed areas, the commit verified and
its result, open QA findings and skipped verification, and the next action.

`start-task` reconciles this file with the real diff (`git status` / `git diff`) when
resuming; `finish-task` overwrites it before committing.

- [ ] The team knows the file location and that it is overwritten, not appended

### 6. Migration patch for the user-level common rules (applied by the owner)

These live outside the repository, in `~/.claude/rules/common/`. Without this patch the
old rules keep launching a second reviewer and the triple review returns.

**`agents.md` and `code-review.md`** — add this condition:

> If the project contains `.claude/agents/qa-engineer.md`, **do not launch
> `code-reviewer`**. Delegate to `qa-engineer` instead; it owns both code review and
> acceptance verification. The PM checks the QA report (evidence, open items, integration
> risk) and does not repeat the same review.

**`development-workflow.md`** — scope down two blanket requirements:

> **Planning documents**: generate PRD / architecture / system_design / tech_doc /
> task_list **only for large efforts** (a new system, a new phase, or a change spanning
> multiple components). For a localized fix, the issue body plus the PR description is
> sufficient.

> **Research & reuse**: GitHub code search and package-registry research are required
> **when the specification is unknown, a new dependency is being introduced, or an approach
> is being selected**. A known, localized fix does not require broad external research.

- [ ] `~/.claude/rules/common/agents.md` patched
- [ ] `~/.claude/rules/common/code-review.md` patched
- [ ] `~/.claude/rules/common/development-workflow.md` patched

### 7. Rollback

Every step is reversible and independent:

1. Revert the `extends` tag to `@v0.5.2` in `guard.policy.yaml` (the CLI may stay at
   0.5.0 — it reads older baselines unchanged).
2. Revert the `model` values in `.claude/agents/*.md` (QA `fable`, BE/DB/FE `sonnet`).
3. Optionally revert the user-level rule patches in `~/.claude/rules/common/`.

Documents added under `docs/` can stay; they are inert if unreferenced.

- [ ] Rollback steps shared with the team

### 8. Comparison metrics after adoption

Measure per **one unit = one issue taken through to QA pass** (not per first
implementation):

- Token volume per issue / per PR, **broken down by model**
- Weekly usage-limit consumption (the increment versus before)
- Number of Compact operations and new-session starts
- Number of HIGH-severity rejections
- Number of bugs found by QA
- Number of defects found **after** a QA pass
- Wall-clock time to completion
- Number of human interventions

> Do not evaluate on the cheapness of the first implementation alone. A cheap first pass
> that needs three rejections costs more than one pass that lands.

- [ ] Baseline recorded before adoption
- [ ] Metrics re-measured after adoption

```yaml
extends:

```
