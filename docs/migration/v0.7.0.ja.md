# v0.7.0 移行ガイド — 既存プロジェクトの差分適用チェックリスト

[English](v0.7.0.md) | **日本語**

対象: v0.6.0 標準で運用中のプロジェクト。
それより古い版から移行する場合は、先に [v0.5.0](v0.5.0.ja.md) / [v0.5.1](v0.5.1.ja.md) /
[v0.5.2](v0.5.2.ja.md) / [v0.6.0](v0.6.0.ja.md) を適用してから本ガイドに進む。

> **まず前提**: リモート参照はタグ固定のため、**何もしなくても壊れない**。追随は任意。

> **`@guardsmith/cli` 0.6.0 以上が必要**。v0.7.0 の baseline は新 check `drift3` を含むため、
> 旧 CLI は strict スキーマで未知の check として拒否する。extends タグを上げる(手順 2)**前に**
> CLI を上げること。

> **破壊的変更: `guard sync` が衝突時に終了コード 1 を返すようになる**。v0.6.0 までは常に 0 だった。
> CI で `guard sync` を(`--write` の有無にかかわらず)回している PJ は、標準変更がクリーンに
> 適用できなくなった時点でそのジョブが落ちる。タグを上げる前に、そのジョブをパイプラインの
> ブロッカーにするか許容にするかを決めておくこと。`guard lint` の終了コードは変えない。

v0.7.0 が変えるのは「**PJ が標準更新をどう取り込むか**」:

- これまでは、マスターの 2 タグ間の差分を読んで標準節を手で反映する運用だった
  (v0.6.0 ガイドが「マスターから `qa-engineer.md` の標準節を手動で反映する」と
  書かざるを得なかったのはこのため)。
- v0.7.0 はこれを **3-way マージ**にする。現行タグのマスターが base、新タグのマスターが theirs、
  PJ リポジトリが ours。
- マージにはテンプレートのプレースホルダを何に置換したかの情報が要るため、PJ は
  `guardsmith.vars.yaml`(コミット対象の辞書)を持つようになる。
- `guard bump <tag>` が一連の作業を 1 コマンドで行う: `extends` タグの書き換え、ファイルのマージ、
  `guardsmith.vars.yaml` と `CLAUDE.md` スタンプの新タグへの更新。

既存 PJ の手順は **2 つだけ**。

## チェックリスト

### 1. `guardsmith.vars.yaml` を生成してレビューする

```
guard sync --init-vars
```

PJ ルートに `guardsmith.vars.yaml` を生成し、sync は実行せずに終了する。
現行タグのマスターと PJ のファイルを突き合わせて各値を推定する。

```yaml
version: 1
standards: v0.6.0
vars:
  PROJECT_NAME: "BizCore"
  OWNER: "Novexar"
  ORG/REPO: "novexar/bizcore"
  "単一システム | モノレポ": "モノレポ"
  FE_STACK: "React 19 + Vite + TailwindCSS v4"
```

キーは `{{ }}` の**内側の文字列そのまま**。スラッシュ入り(`ORG/REPO`)も選択式
(`"単一システム | モノレポ"`)もそのまま使う。`standards` は PJ を展開した元のタグで、
`--init-vars` は `CLAUDE.md` 末尾スタンプから読む。

> **生成ファイルは必ずレビューする。** 推定はあくまで best effort であり、値が誤っていると
> 後で `guard bump` が PJ の文言を静かに書き換えてしまう。
>
> - 決められなかったキーは `TODO` になる。**`TODO` が 1 つでも残っている間、あるいは標準が
>   使うプレースホルダが `vars` に 1 つでも足りない間、`guard bump` と `guard sync --write`
>   は終了コード 2 で止まる。** dry-run と `guard lint` は従来どおり動き、足りないキーを
>   名指しで報告する。書き込みだけを拒否するのは、未確定の値がそのまま PJ へ書き込まれて
>   しまうため。
> - 候補が複数あったキーは最頻値が入り、全候補がキーの隣にコメントで並記される。
>   正しいものを選んでコメントを消すこと。
> - 秘密パターンに一致した値は意図的に `TODO` へ落とされる。このファイルはコミット対象である。
>   トークン・API キー・パスワード・接続文字列を絶対に入れない。
> - `CLAUDE.md` に末尾スタンプが無い場合、`--init-vars` は現行タグを判定できず終了コード 2 で
>   止まる。`standards:` を手書きしてから再実行する。
> - `guardsmith.vars.yaml` が既にある場合、`--init-vars` は**上書きせず**終了コード 2 で終わる。

v0.7.0 以降に `guard new` で作成した PJ は既にこのファイルを持つため、本手順は不要。

- [ ] `guardsmith.vars.yaml` を生成した
- [ ] `TODO` をすべて解消した
- [ ] 曖昧候補のコメントをすべて確認して削除した
- [ ] 秘密情報が含まれていない
- [ ] `standards` が `CLAUDE.md` 末尾スタンプのタグと一致している
- [ ] ファイルをコミットした

### 2. dry-run してから bump する

```
guard sync          # dry-run。計画と衝突予測を表示し、ファイルは書かない
guard bump v0.7.0   # 適用。extends タグと guardsmith.vars.yaml も更新する
```

必ず dry-run を先に回す。`--write` なしの `guard sync` はファイルに一切触れず、
すべてクリーンに適用できるなら 0、1 ファイルでも衝突すれば 1 を返す。

`guard bump v0.7.0` は `guard.policy.yaml` 内の `github:novexar/guardsmith...@vX.Y.Z` 参照
(baseline / frontend / PJ が自分で書いた `drift3` の source)を書き換え、ファイルをマージし、
**`.claude/skills/**` の節単位同期も新タグのマスターに対して同時に実行し**、
`guardsmith.vars.yaml` の `standards` と
`CLAUDE.md` スタンプを新タグにする。1 コマンドで `guard sync --write` と同じ範囲を終えるので、
後から別手順を実行し忘れることがない。標準が `novexar/guardsmith` 以外にある場合は
`--repo <owner>/<repo>` を使う。

> **追随する標準リポジトリは 1 つだけ。** `guardsmith.vars.yaml` が持つ `standards` タグは
> 1 本なので、そのタグが指せる配布元も 1 つに限られる。別リポジトリを指す `drift3`
> (Layer2 のオーバーレイ `github:novexar/guardsmith-private//standards@v3.0.0` など)は
> **bump の対象外**で、自分のタグと突き合わせることもしない。警告を出したうえで、その
> ルール自身が固定しているタグのままにする。同じ理由で、対象リポジトリ向けの `drift3` は
> ポリシー全体で **1 本まで**。2 本以上あると policy エラー(終了コード 2)になる。

**衝突があった場合、`guard bump` は policy も vars もファイルも skills も一切書かず**、衝突ファイルを
列挙して 1 を返す。**列挙されたファイルだけ**を解決し、その後 `guard sync --write` で残りを適用する。
`<<<<<<<` / `|||||||` / `=======` / `>>>>>>>` マーカー入りで書き出したい場合は
`--conflict-markers` を付ける(この場合も終了コードは 1 のまま)。

`guard sync --write` も同じ方針で、先に 3-way の計画を作り、衝突があれば節単位モードの
適用も止める。中途半端に適用されたツリーが残ることはない。実際に書くファイル
(マージ結果・節単位の復元・`guardsmith.vars.yaml`・`CLAUDE.md` スタンプ)は **1 つの
バッチ**として扱い、全件を一時ファイルへ書き切ってから確定する。確定の途中で失敗した
場合は確定済みの分を元へ戻すため、「一部のファイルだけ新タグ」という状態は生じない。

| コマンド           | 終了コード 0           | 終了コード 1                      | 終了コード 2                            |
| ------------------ | ---------------------- | --------------------------------- | --------------------------------------- |
| `guard sync`       | 衝突なし(dry-run 含む) | 衝突あり                          | 実行エラー / `--write` で vars が未完成 |
| `guard bump <tag>` | 適用完了               | 衝突あり(policy も vars も未変更) | 実行エラー / vars が未完成              |

フラグ:

```
guard sync  [--root <dir>] [--policy <file>] [--write] [--no-cache] [--no-gitignore]
            [--conflict-markers] [--init-vars]
guard bump  <tag> [--root <dir>] [--policy <file>] [--repo <owner>/<repo>]
            [--no-cache] [--no-gitignore] [--conflict-markers]
```

- [ ] `@guardsmith/cli` を 0.6.0 以上へ上げた(Action の `cli-version` / `release-tag` を
      固定している場合はそちらも)
- [ ] `guard sync` の dry-run 出力を確認した
- [ ] `guard bump v0.7.0` を実行し、衝突を解決した
- [ ] 確認コマンド: `npx @guardsmith/cli lint`
- [ ] CI で `guard sync` を回しているジョブが新しい終了コード 1 を扱えることを確認した
- [ ] 別の標準リポジトリ向け `drift3` を継承している場合、新たに出る警告を確認した
      (そのルールは自分の固定タグのままで、bump の対象外になる)

### 3. 何が自動で入り、何が衝突になるか

マージはファイル単位で、ファイル内は変更ブロック単位で行われる:

| 状況                                                                  | 結果                                                                                   |
| --------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| PJ が触っていない標準節がマスターで変更された                         | 自動で適用される                                                                       |
| PJ が書き換えた節がマスターでも変更された                             | **衝突** — そのファイルは無変更のまま報告される                                        |
| PJ が書き換えた節がマスターでは無変更                                 | PJ の文言がそのまま残る                                                                |
| 新マスターにのみあるファイル(例 `docs/SETUP.md`)                      | 追加される                                                                             |
| マスターから消えたファイル                                            | **自動削除しない**。`info` で報告するので、同意するなら自分で消す                      |
| PJ が意図的に削除したファイル(BE 不在 PJ の `backend-engineer.md` 等) | `info` 付きで skip。再作成されない                                                     |
| PJ にしか無いファイル                                                 | 一切触らない                                                                           |
| `vars` に登録の無いプレースホルダ                                     | `{{KEY}}` のリテラルのまま残り `info` で報告される。埋めるまで**書き込みは拒否される** |

`<!-- gen: 採用しない層は行ごと削除 -->` の指示に従って消した表の行も同じ扱い。削除は PJ の変更として
残り、マスターがその行を変更した場合にのみ衝突になって手動判断に回る。

`guard lint` でも `drift3` が同じ状態を報告する:

```
WARN  drift/standards-sync  standards v0.6.0 → v0.7.0 not applied (4 files, applies cleanly) — run: guard bump v0.7.0
INFO  drift/standards-sync  standards v0.6.0 → v0.7.0 needs manual merge (conflicts in .claude/agents/qa-engineer.md)
INFO  drift/standards-sync  guardsmith.vars.yaml not found — falling back to section comparison. run: guard sync --init-vars
INFO  drift/standards-sync  2 placeholder(s) missing from guardsmith.vars.yaml: FE_STACK, DB — guard sync --write and guard bump refuse to run until filled
```

既存の節単位の `drift` チェック(`.claude/skills/**`、`allow_sections`)は無変更であり、
`drift3` ルールを持たないポリシーに対する `guard sync` の挙動も変わらない。

- [ ] dry-run の計画を読み、どのファイルが衝突として報告されたかを把握した

### 4. v0.6.0 の標準を手動で取り込んだ PJ の注意

一部の PJ(例: `cctower`)は sync を待たず v0.6.0 の標準節を手で反映した。それで問題ない。
むしろ 3-way マージが最も得意とする状況である:

- 手で反映した内容が**旧→新マスターの差分と一致する**場合、マージは「ours と theirs が同じ変更を
  した」と判断し、**衝突にならない**(二重適用もされない)。
- **一致しない**場合(言い換えた・順序を変えた・一部だけ取り込んだ)、そのファイルは**衝突**になる。
  `v0.7.0` のマスターと自分の版を比べ、どちらの文言を残すか判断する。

つまり手動移行した PJ が不利になることはないが、最も手を入れたファイルでいくつか衝突が出る前提で
臨むこと。

- [ ] 衝突したファイルを `v0.7.0` のマスターと比較した

### 5. 切り戻し手順

どちらの手順も元に戻せる。リポジトリ外には何も変更を加えない:

1. `guard.policy.yaml` の `extends` タグを `@v0.6.0` に戻す。
2. `guardsmith.vars.yaml` の `standards` を `v0.6.0` に戻す(`CLAUDE.md` 末尾スタンプも同時に戻す。
   両者は一致していなければならない)。
3. マージで入ったファイル変更を元に戻したい場合は git で revert する。

CLI は 0.6.0 以上のままでよい(v0.6.0 の baseline もそのまま読める)。切り戻し後に
`guardsmith.vars.yaml` を残しておいても無害である(`drift3` ルールが有効なときにしか読まれない)。

- [ ] 切り戻し手順をチームで共有した
