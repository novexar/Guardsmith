# v0.6.0 移行ガイド — 既存プロジェクトの差分適用チェックリスト

[English](v0.6.0.md) | **日本語**

対象: v0.5.2 標準で運用中のプロジェクト。
それより古い版から移行する場合は、先に [v0.5.0](v0.5.0.ja.md) / [v0.5.1](v0.5.1.ja.md) /
[v0.5.2](v0.5.2.ja.md) を適用してから本ガイドに進む。

> **まず前提**: リモート参照はタグ固定のため、**何もしなくても壊れない**。追随は任意。

> **`@guardsmith/cli` 0.5.0 以上が必要**。v0.6.0 の baseline は新 check `import-budget` を
> 含むため、旧 CLI は strict スキーマで未知の check として拒否する。extends タグを上げる
> (手順 9)**前に** CLI を上げること。

v0.6.0 は「**誰が品質を確認するか**」と「**どれだけ文脈を常駐させるか**」を整理する:

- コードレビューを PM から**独立 QA(`qa-engineer`)**へ移し、QA がコードレビューと受入検証の
  両方を担う。
- エンジニアのモデル方針を変更(BE / DB は `opus`、FE は `sonnet`、QA は `opus`)。
- `CLAUDE.md` の `@` インポートを「常駐が必要な 1 文書」だけに絞る。
- 行数規則(50 / 800 / 4)を閾値ではなく**目安**にする。

## チェックリスト

| `qa-engineer`        | `fable`             | `opus`                                               |
| `backend-engineer`   | `sonnet`            | `opus`                                               |
| `db-engineer`        | `sonnet`            | `opus`                                               |

      (frontmatter の値だけを証拠にしない)

### 2. qa-engineer の責務を更新する

`qa-engineer` は実装から独立した唯一の品質ゲートになる。**コードレビュー**(競合・冪等性・
データ整合性・権限・入力境界・性能・設計欠陥)と**動作・受入検証**(受入条件、正常/異常系、
統合、重要ユーザーフロー、回帰、FE は a11y)の両方が必須責務。加えて「再発防止の検証条件」表を持つ。

標準節の取り込みは次で行う:

```
guard sync --write
```

`guard sync` が上書きするのは標準節のみで、**PJ 固有節は上書きしない**。
まず `--write` なし(dry-run)で差分を確認してから適用する。

> **注意**: `guard sync` が復元するのは、ポリシーの `drift` ルールの `paths` に一致するファイルだけ。
> baseline の drift ルールは `.claude/skills/**` のみを対象にしているため、**`.claude/agents/**` は
> 既定では同期されない**。自 PJ のポリシーの drift `paths` に `.claude/agents/**` を追加するか、
> マスター(タグ `v0.6.0` の `standards/.claude/agents/qa-engineer.md`)から標準節を手動で反映する。

- [ ] `.claude/agents/qa-engineer.md` に新しい責務と報告形式が入っている
- [ ] PJ 固有節が残っている

### 3. CLAUDE.md / DEVELOPMENT_WORKFLOW.md の `@` 参照を見直す(手動)

`@docs/...` は**インポート**であり、毎セッション起動時にファイル全体が読み込まれて常駐する。
つまり「120 行を超えたので docs へ退避して `@` 参照にする」では**コンテキストは減らない**。

次のように、通常パス + 「いつ読むか」へ変更する:

| 参照                            | 変更後                                                     |
| ------------------------------- | ---------------------------------------------------------- |
| `@docs/CODING_STANDARDS.md`     | `@` のまま(常駐させる唯一の文書)                           |
| `@docs/REQUIREMENTS.md`         | `docs/REQUIREMENTS.md` — Issue 起票時・受入条件の確認時    |
| `@docs/ARCHITECTURE.md`         | `docs/ARCHITECTURE.md` — 構成変更・新コンポーネント追加時  |
| `@docs/DEVELOPMENT_WORKFLOW.md` | `docs/DEVELOPMENT_WORKFLOW.md` — 着手時・PR 作成時・委任時 |
| `@docs/CI_CD.md`                | `docs/CI_CD.md` — `make ci` 失敗時・CI 構成変更時          |
| `@docs/INFRA.md`                | `docs/INFRA.md` — インフラ変更時                           |

`CLAUDE.md` 本体は 120 行以内を維持するが、**行数だけで軽量とは判断しない**。
常駐量は `guard lint` で確認する。新ルール `claude-md/import-budget` が info で表示する:

```
INFO  claude-md/import-budget CLAUDE.md — resident context: 2 files, 7633 chars (≈1909 tokens, rough estimate)
  - docs/CODING_STANDARDS.md: 5547 chars
  - CLAUDE.md: 2086 chars
```

**32,000 文字**を超えると warn になる。トークン数は `chars / 4` の粗い目安であり実測ではない。

`@scope/pkg` のようなパッケージ名をバッククォート無しで書くと Claude Code もインポートとして
読みに行くため、本ルールは `unresolved import` の info を出す。公式仕様どおりバッククォートで
囲むこと(取り込まずにパスを書く方法として文書化されている)。

- [ ] `CLAUDE.md` で `@` が付いているのは `docs/CODING_STANDARDS.md` のみ
- [ ] 他の文書は通常パス + 「読む条件」で記載されている
- [ ] `import-budget` の info を見て常駐量が 32,000 文字を超えていないことを確認した
- [ ] `@scope/pkg` 等のパッケージ名をバッククォートで囲んだ

### 5. .guardsmith/state/ の利用を始める

Issue ごとの作業状態を `.guardsmith/state/<issue番号>.md` に
**現在状態として上書き更新**する(日誌ではない)。`.guardsmith/` は `.gitignore` 済み。

記録項目: Issue 番号 / ブランチ / HEAD / 未コミット変更 / 受入条件と重要制約 /
決定事項と却下理由 / 変更箇所・検証対象コミットと結果 / 未解決 QA 指摘と未実施検証 / 次の作業。

`start-task` は再開時にこのファイルと実差分(`git status` / `git diff`)を照合し、
`finish-task` はコミット前に上書き更新する。

- [ ] ファイルの場所と「追記ではなく上書き」であることをチームで共有した

### 6. ユーザー共通ルール側の移行パッチ(オーナーが適用)

これらはリポジトリ外の `~/.claude/rules/common/` にある。**このパッチを当てないと、
旧ルールが二人目のレビュアを起動し続け、三重レビューが復活する。**

**`agents.md` / `code-review.md`** — 次の条件を追加する:

> プロジェクトに `.claude/agents/qa-engineer.md` が存在する場合は、**`code-reviewer` を起動しない**。
> 代わりに `qa-engineer` への委任で代替する(コードレビューと受入検証の両方を QA が担う)。
> PM は QA 報告の確認(検証証拠・未解決事項・統合リスク)に徹し、同じレビューを繰り返さない。

**`development-workflow.md`** — 一律要求を 2 点だけ限定する:

> **計画文書**: PRD / architecture / system_design / tech_doc / task_list の生成は、
> **大型案件(新システム・新フェーズ・複数コンポーネントにまたがる変更)に限定する**。
> 局所的な修正は Issue 本文 + PR 本文で足りる。

> **調査・再利用**: GitHub コード検索・パッケージレジストリ調査は、
> **未知の仕様・新規依存の導入・方式選定のときに必須**とする。
> 既知の局所修正に広範な外部探索は求めない。

- [ ] `~/.claude/rules/common/agents.md` にパッチを当てた
- [ ] `~/.claude/rules/common/code-review.md` にパッチを当てた
- [ ] `~/.claude/rules/common/development-workflow.md` にパッチを当てた

### 7. 切り戻し手順

各ステップは独立しており、いつでも戻せる:

1. `guard.policy.yaml` の `extends` タグを `@v0.5.2` に戻す(CLI は 0.5.0 のままでよい。
   旧 baseline もそのまま読める)。
2. `.claude/agents/*.md` の `model` を戻す(QA は `fable`、BE / DB / FE は `sonnet`)。
3. 必要なら `~/.claude/rules/common/` のパッチを戻す。

`docs/` に追加した文書は残してよい(参照されなければ影響しない)。

- [ ] 切り戻し手順をチームで共有した

### 8. 導入後の比較指標

**QA 合格までを 1 件**として測る(初回実装の完了ではない):

- Issue / PR あたりの**モデル別**トークン量
- 週次利用枠の増分(導入前との差)
- Compact 実施回数・新規起動回数
- HIGH 指摘による差戻し数
- QA が発見したバグ数
- **合格後**に見つかった不具合数
- 完了までの所要時間
- 人間の介入回数

> **初回実装の安さだけで評価しない**。3 回差戻される安い初回より、1 回で通る実装のほうが安い。

- [ ] 導入前のベースラインを記録した
- [ ] 導入後に再計測した
