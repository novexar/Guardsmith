# v0.5.2 Migration Guide — incremental checklist for existing projects

**English** | [日本語](v0.5.2.ja.md)

Audience: projects operating on the v0.5.1 standards.
If you are migrating from an older release, apply the [v0.5.0](v0.5.0.md) and
[v0.5.1](v0.5.1.md) migration guides first, then continue with this guide.

> **First, the baseline**: remote references are tag-pinned, so **nothing breaks if you do
> nothing**. Catching up is optional.

The delta from v0.5.1 is scan scope: `guard lint` / `guard sync` now honour `.gitignore`,
and the policy gained a top-level `ignore` key.

## Checklist

### 1. Bump the extends tag to v0.5.2

```yaml
extends:
  - github:novexar/guardsmith//presets/baseline.yaml@v0.5.2 # ← changed from @v0.5.1
```

The baseline's `security/no-secrets-in-context` now excludes `.claude/worktrees/**`
explicitly, so the false positives from agent worktrees stop even on an older CLI.

- [ ] Changed the extends tag to `@v0.5.2`

### 2. Update the CLI to 0.4.0

```bash
npx @guardsmith/cli@0.4.0 lint
```

In a workflow using the Action, either pin `cli-version: "0.4.0"` or move to
`uses: novexar/Guardsmith@v0.5.2` (its default is already 0.4.0).

From 0.4.0, scanning is limited to **files that could be committed**: `.gitignore` is
honoured (nested `.gitignore` files too) and `.git/` is always excluded.

Seven of the eight checks enumerate files with globs and follow `.gitignore`. `json-path`
reads one fixed path directly and is the only exception:

| Check           | Follows `.gitignore` | What it means for a `.gitignore`'d path                        |
| --------------- | -------------------- | -------------------------------------------------------------- |
| `file-exists`   | yes                  | Counts as **missing** → the rule reports it                    |
| `file-absent`   | yes                  | Counts as **absent** → no finding, even if the file is on disk |
| `content-match` | yes                  | Not scanned (an empty match set is reported as `info`)         |
| `max-lines`     | yes                  | Not scanned                                                    |
| `frontmatter`   | yes                  | Not scanned                                                    |
| `drift`         | yes                  | Not compared against the master                                |
| `secret-scan`   | yes                  | Not scanned                                                    |
| `json-path`     | **no**               | Read directly, so it still fires                               |

Three consequences are worth checking against your policy:

- `secret-scan` no longer reports values inside `.gitignore`'d files such as
  `.claude/settings.local.json`
- `file-exists` treats a `.gitignore`'d path as missing. If a rule of yours required a file
  that is in `.gitignore`, it now fails — either remove the exclusion or drop the rule
- `file-absent` is the mirror image: baseline's `hygiene/no-env-file` finds nothing once
  `.env` is in `.gitignore`. That is intended — the rule exists to stop `.env` being
  committed, and an ignored file cannot be — but it does mean the warning disappears
- `json-path` is deliberately exempt, so `security/dangerous-permissions` keeps working on
  projects that keep `.claude/settings.json` local

- [ ] CLI is 0.4.0 (`npx @guardsmith/cli version`)
- [ ] `guard lint` findings are as expected

### 3. Add `ignore:` for directories that are not in .gitignore (optional)

`ignore` is a list of globs excluded from every scan. Unlike `rules`, it is
**concatenated** across `extends` layers (duplicates are removed), so an organization
overlay can add exclusions without a project having to repeat them.

```yaml
version: 1
target: claude-code
extends:
  - github:novexar/guardsmith//presets/baseline.yaml@v0.5.2
ignore:
  - "vendor/**"
  - "**/__snapshots__/**"
rules: []
exemptions: []
```

Use it only for what `.gitignore` does not already cover — anything listed in
`.gitignore` is excluded without configuration.

- [ ] Added `ignore:` if needed

### 4. Repositories with agent worktrees

A layout where per-agent worktrees live under the repository root, each carrying its own
`.venv` / `node_modules`, used to be walked in full on every run (tens of thousands of
files), which made `guard lint` take over a minute and made `secret-scan` report things
like `.venv/Scripts/python.exe`.

```
<repo>/
├── .gitignore            # contains `.claude/worktrees/`
└── .claude/worktrees/
    ├── agent-a/          # a full copy of the repository + .venv / node_modules
    └── agent-b/
```

With the line already in `.gitignore`, 0.4.0 prunes those trees during traversal — no
policy change is required. If the worktrees are **not** in `.gitignore`, add them to the
policy's `ignore` instead.

- [ ] `guard lint` finishes in a realistic amount of time

### 5. When you need the full scan: `--no-gitignore`

```bash
npx @guardsmith/cli lint --no-gitignore
npx @guardsmith/cli sync --no-gitignore
```

Restores pre-0.4.0 behaviour and scans `.gitignore`'d files as well. Use it to audit what
is sitting in local-only files (for example, to confirm no credential leaked into
`.claude/settings.local.json`) — not as the everyday setting, since it is slow and prone
to false positives. The policy's `ignore` and the `.git/` exclusion still apply.

- [ ] Ran an audit with `--no-gitignore` once (optional)
