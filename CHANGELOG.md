## v0.7.1 (2026-09-25)

A documentation-accuracy release. The v0.7.0 migration guide and the `init-project` skill
both told projects to "check the diff and the predicted conflicts with `guard sync`, then
run `guard bump <tag>`" — but `guard sync` measures against the tag the policy **currently**
pins, so on a project already in step with its tag it reports zero changes while the bump
goes on to merge plenty. `guard bump <tag> --dry-run` closes that gap: it resolves the new
tag, builds the real plan, and writes nothing.

### Added

- `guard bump <tag> --dry-run`: resolves the master at the **new** tag, builds the same
  3-way and section-level plan the real run would, and prints it together with the predicted
  conflicts and the `guard.policy.yaml` lines it would rewrite — while writing **nothing**
  (no policy, no `guardsmith.vars.yaml`, no stamp, no file, no temporary file). It returns
  the exit code the real run would: `0` when the tag applies cleanly, `1` on conflicts, `2`
  on a run-time error (an incomplete `vars`, a `TODO`, a roll-back, and so on are judged
  exactly as they are when applying). Combining it with `--conflict-markers` is a usage
  error (`2`)

### Changed

- The catch-up procedure in docs/migration/v0.7.0.md and the standards' `init-project` skill
  is now `guard bump <tag> --dry-run` → `guard bump <tag>`. `guard sync` (dry-run) is
  documented for what it actually does: check what is still unapplied **at the current tag**,
  which is not a preview of the bump
- Bumped remote-reference tags and generated-artifact stamps to v0.7.1 (baseline drift
  sources / policy generated by `guard new` / docs examples / the Action's `release-tag`
  default)
- npm: `@guardsmith/core` / `@guardsmith/cli` 0.6.1 (the Action's `cli-version` default is
  also 0.6.1)

### Fixed

- **A failed remote fetch now exits 2 instead of 127.** The CLI entry point called
  `process.exit()`, which tore the process down while undici still had open handles; on
  Windows libuv aborted with `Assertion failed: !(handle->flags & UV_HANDLE_CLOSING)` and
  the shell saw 127. It now sets `process.exitCode` and lets the event loop drain, so a
  missing tag or an unreachable standards repository is reported as the run-time error it
  is (`guard lint` / `sync` / `bump` alike)
- **`--dry-run` is rejected everywhere except `guard bump`.** The flag was parsed for every
  subcommand but only read by `bump`, so `guard sync --write --dry-run` silently _wrote_ —
  the section-level restore overwrote project edits and exited 0. `guard sync`, `guard lint`,
  `guard new` and `guard explain` now fail with `unknown flag: --dry-run` (exit 2)

## v0.7.0 (2026-09-24)

A release about **keeping a project in step with the standards it was generated from**.
Until now a project could be measured against the master, but there was no way to take a
master change into a repository that had already been filled in — the placeholders were
gone. `guardsmith.vars.yaml` records what each placeholder was replaced with, which makes
a real three-way merge possible: `guard sync` and the new `guard bump` apply the
standards' change while the project's own edits stay put. For the catch-up steps for
existing projects, see docs/migration/v0.7.0.md.

### Added

- `guardsmith.vars.yaml` at the project root (committed): `version` / `standards` (the tag
  the project was generated from, pinned as `vX.Y.Z`) / `vars` (placeholder key → value).
  It is the only record of what `{{PROJECT_NAME}}` and friends became, and the input to
  every three-way operation
- `guard sync` gains a **3-way mode**, used when the effective policy has a `drift3` rule.
  The old master (at the `standards` tag) and the new master (at the source's tag) are both
  normalized with the project's `vars`, and the difference between them is merged into the
  project: project edits are kept, only the standards' change is applied. Section mode
  (`check: drift`) keeps working exactly as before, in the same run
- `guard sync --init-vars`: infers `guardsmith.vars.yaml` for a project initialized before
  v0.7.0, by matching each placeholder position in the old master against the project's
  corresponding line. Values it cannot determine become `TODO`, ambiguous ones take the
  most frequent candidate with every candidate listed in a comment, and anything matching a
  secret pattern is dropped to `TODO` rather than written down
- `guard sync --conflict-markers` / `guard bump --conflict-markers`: write the conflicting
  files with `<<<<<<<` / `|||||||` / `=======` / `>>>>>>>` markers instead of leaving them
  untouched. The exit code stays 1 and the standards tag is not advanced
- `guard bump <tag> [--repo <owner>/<repo>]`: rewrites the pinned tags in
  `guard.policy.yaml` (plain text replacement — comments, indentation and key order are
  preserved), applies the standards' change through the same 3-way plan, **also runs the
  section-level sync for `.claude/skills/**` against the master at the new tag**, and
  advances the `standards` tag and the `CLAUDE.md` stamp — one command, nothing left to run
  afterwards. On a conflict it writes **nothing** and exits 1
- New check `drift3` (`with: { source, paths }`): reports a standards change that has not
  been applied yet at the rule's severity — `standards v0.6.0 → v0.7.0 not applied
(N files, applies cleanly) — run: guard bump v0.7.0` — and one that needs hands as `info`.
  Without `guardsmith.vars.yaml` it falls back to the section comparison and points at
  `--init-vars`
- baseline: `drift/standards-sync` (warn, `check: drift3`) covering `CLAUDE.md`,
  `DESIGN.md`, `docs/**/*.md` and `.claude/agents/**/*.md`. `drift/skills-sync` stays on
  section mode — one release does not change the meaning of both
- baseline `security/no-secrets-in-context` also scans `guardsmith.vars.yaml`, which is
  committed and would otherwise be a quiet leak path
- `guard new` writes a `guardsmith.vars.yaml` skeleton (`standards: "v0.7.0"`, empty
  `vars`) for init-project to fill in

### Changed

- The project is never rolled back silently. When `guardsmith.vars.yaml` is at a **newer**
  tag than the policy distributes — a bump whose policy write failed, or a reverted or
  hand-edited policy — a plain three-way would run "new → old" and undo the standards.
  `guard sync` and `guard bump` now refuse with exit 2 and print no plan, `guard lint`
  reports it as a `warn`, and `--allow-downgrade` is required to go back on purpose
- `guard bump <tag>` resolves the **`extends` refs** of the target repository at the new tag
  as well, so a baseline that widened a rule's `paths` is honoured by the same bump instead
  of only from the next run
- Only the standards repository named by `--repo` (default `novexar/guardsmith`) is
  followed. `guardsmith.vars.yaml` records a single `standards` tag, so a `drift3` rule
  pointing at another repository — a Layer 2 overlay such as
  `github:novexar/guardsmith-private//standards@v3.0.0` — keeps its own pinned tag, is
  reported with a warning, and is never resolved against yours. For the same reason a
  policy may carry at most one `drift3` rule for the target repository
- Writes are refused while the project's values are incomplete: `guard sync --write` and
  `guard bump` exit 2 when a `vars` value is still `TODO` or a placeholder used by the
  standards is missing. A dry-run and `guard lint` still report it as `info` and name the
  keys — only writing is blocked, because an unfilled value would otherwise be written into
  the project verbatim
- Nothing is half-applied: `guard sync --write` builds the 3-way plan first, so a conflict
  suppresses the section-level restore as well, and everything a write touches — merged
  files, section restores, `guardsmith.vars.yaml` and the `CLAUDE.md` stamp — goes out as a
  single batch that is staged first and rolled back if committing any one file fails
- `paths` patterns may no longer contain a `..` segment, and every write is confined to the
  project root at run time. `guard sync` writes to the paths a glob matched, and a policy
  can be inherited from a remote `extends`, so a pattern like `../**/*.md` was a way to
  write outside the repository

- Standards / init-project: the interview results are now **recorded** in
  `guardsmith.vars.yaml` as they are applied, and the "following the master" procedure is
  `guard bump <tag>` instead of a manual diff
- Bumped remote-reference tags and generated-artifact stamps to v0.7.0 (baseline drift
  sources / policy generated by `guard new` / docs examples / the Action's `release-tag`
  default)
- npm: `@guardsmith/core` / `@guardsmith/cli` 0.6.0 (the Action's `cli-version` default is
  also 0.6.0)

### Breaking

- **`guard sync` exits 1 when there are conflicts.** It always returned 0 before, so a CI
  job running `guard sync` without `--write` as a check now fails when the standards and
  the project touched the same lines. That is the intent — the alternative is drifting
  further apart in silence — but it has to be handled before bumping the tag
- **baseline v0.7.0 requires `@guardsmith/cli` 0.6.0 or newer.** It contains the `drift3`
  check, and an older CLI rejects it as an unknown check under its strict schema. Upgrade
  the CLI before bumping the `extends` tag
- **`guard new` produces one more file.** `guardsmith.vars.yaml` is part of the generated
  project and is meant to be committed; init-project fills it in

## v0.6.0 (2026-09-24)

A release about **how much context stays resident** and **who checks quality**. `guard lint`
gains `import-budget`, which measures a `CLAUDE.md` together with everything its `@path`
imports pull in — a 60-line `CLAUDE.md` importing five documents is not a small one, and the
line count alone never showed that. The standards move code review to an independent QA
agent. For the catch-up steps for existing projects, see docs/migration/v0.6.0.md.

### Added

- New check `import-budget`: measures the resident total of an entry file plus every file
  reached through `@` imports. Always reports one `info` —
  `resident context: N files, X chars (≈Y tokens, rough estimate)` with a per-file
  breakdown — and reports at the rule's severity when `max_chars` is exceeded.
  `with: { path, max_chars?, max_depth? }`; `max_depth` defaults to the documented 4 hops
- Import semantics follow the Claude Code memory docs: `@path` anywhere in the file,
  relative paths resolved against the importing file's directory, code spans and fenced
  code blocks skipped. Cycles, unresolved targets and depth-limit stops are reported as
  `info`. References that resolve outside the scan root (`..`, absolute paths, `~/`,
  backslashes, or a symlink pointing out) are **never read**, only reported
- baseline: `claude-md/import-budget` (warn, `max_chars: 32000`) next to
  `claude-md/thin-diff`
- Standards v0.6.0: code review moves from the PM to an independent `qa-engineer` that owns
  both review and acceptance verification; a new engineer model policy (BE/DB `opus`,
  FE `sonnet`, QA `opus`); `@` imports in `CLAUDE.md` narrowed to the single document that
  must stay resident; first-time setup split out into `docs/SETUP.md`; per-issue working
  state recorded under `.guardsmith/state/`

### Changed

- Standards: `@docs/...` is documented as an **import**, so moving content into `docs/` and
  referencing it with `@` does not reduce context. Only `docs/CODING_STANDARDS.md` stays
  behind `@`; every other document is listed with a plain path and a "when to read it" note
- Standards: the line-count rules (50 / 800 / 4) become **guidelines**, not thresholds
- baseline `claude-md/thin-diff`: the description now says it only counts the lines of the
  file itself, and points at `claude-md/import-budget` for the resident volume
- Bumped remote-reference tags and generated-artifact stamps to v0.6.0 (baseline drift
  source / policy generated by `guard new` / docs examples / the Action's `release-tag`
  default)
- npm: `@guardsmith/core` / `@guardsmith/cli` 0.5.0 (the Action's `cli-version` default is
  also 0.5.0)

### Breaking

- **Policy schema is strict again.** Unknown keys under `with` and unknown top-level keys on
  a rule are now **parse errors** with the offending path (`rules.0.with: Unrecognized key:
"limt"`). They were silently dropped before, because `Rule` was composed as
  `discriminatedUnion(...).and(RuleBase)` and the intersection lost the branch-level strict
  check. A policy carrying a typo that used to load now fails to load — which is the
  documented behaviour ("unknown keys are rejected; typos become errors")
- **baseline v0.6.0 requires `@guardsmith/cli` 0.5.0 or newer.** It contains the
  `import-budget` check, and an older CLI rejects it as an unknown check under its strict
  schema. Upgrade the CLI before bumping the `extends` tag
- **Package names in `CLAUDE.md` need backticks.** `@` is recognized anywhere in the file
  (including mid-sentence, which Japanese prose requires), so `@scope/pkg` written bare is
  read as an import — by Claude Code as well — and `import-budget` reports it as
  `unresolved import`. Wrap it in backticks, the officially documented way to mention a
  path without importing it

## v0.5.2 (2026-09-24)

A release that narrows what `guard lint` / `guard sync` walk to **files that could be
committed**. Repositories that keep large ignored trees under the repository root (agent
worktrees with their own `.venv` / `node_modules`) no longer pay for them on every run,
and `secret-scan` stops reporting files that never reach the repository. For the catch-up
steps for existing projects, see docs/migration/v0.5.2.md.

### Added

- Policy: a top-level `ignore` key (array of globs) excluded from every scan. Unlike
  `rules`, it is **concatenated** across `extends` layers (duplicates removed), so an
  organization overlay's exclusions reach every project
- `guard lint` / `guard sync`: `--no-gitignore` restores the full scan (same handling as
  `--no-cache`). The policy `ignore` and the `.git/` exclusion still apply
- `@guardsmith/core`: `runLint(policy, root, now?, { gitignore })` and
  `planSync(policy, root, { gitignore })`; the new `glob` module is exported

### Changed

- All file walking now honours `.gitignore` by default, including nested `.gitignore`
  files, and always excludes `.git/`. `secret-scan` therefore skips paths such as
  `.claude/settings.local.json`, and `file-exists` treats a `.gitignore`'d path as missing
- Ignored trees are **pruned during traversal**, not filtered afterwards. On a fixture with
  a 5,000-file fake `.venv`, walking `.claude/**` drops from 8.6 ms to 0.7 ms
- baseline `security/no-secrets-in-context`: added `!.claude/worktrees/**` to `paths`
  (matching presets/self.yaml) so agent worktrees are excluded on older CLIs too.
  The `ignore` key is deliberately **not** used in baseline — CLI 0.3.0 rejects unknown
  keys under its strict schema
- Bumped remote-reference tags and generated-artifact stamps to v0.5.2 (baseline drift
  source / policy generated by `guard new` / docs examples / the Action's `release-tag`
  default)
- npm: `@guardsmith/core` / `@guardsmith/cli` 0.4.0 (the Action's `cli-version` default is
  also 0.4.0). **0.4.0 was never published to npm** — it was superseded by 0.5.0, released
  the same day with v0.6.0. Use 0.5.0 or newer

## v0.5.0 (2026-09-16)

A major overhaul of the standards (consolidating PRs #3–#7). The standards reference tag
(`STANDARDS_TAG`) is updated to v0.5.0. For the catch-up steps for existing projects, see
docs/migration/v0.5.0.md (tag pinning means nothing breaks if you do nothing; catching up
is optional and can be applied incrementally).

### Added

- **A: Frontend UI foundation standard**: adopted shadcn/ui + Tailwind + TanStack as the
  standard stack. New `presets/frontend.yaml` (only projects with a FE add it to
  `extends`; it is kept out of the baseline to avoid false warnings for BE-only
  projects). Details: standards/docs/FRONTEND_STANDARDS.md
- **C: ponytail adoption** (over-implementation restraint): `.claude/settings.json`
  auto-registers the marketplace, and `finish-task` runs `/ponytail-review` before its
  quality gate. Tests, input validation, security, and a11y are explicitly excluded from
  reduction
- **D: DESIGN.md practice**: added a design-spec template based on awesome-design-md-jp
  (including Japanese UI specs) to the standards. Concretized per project by init-project
- **F: standardized issue templates and an interface for external integrations**: three
  types — feature / bug / chore — with fixed headings (the old task.md is removed).
  Unified `start-task` branch naming as `<type>/<issue number>-<slug>` (a contract that
  lets external tools resolve the issue number from the branch name). Bundled an HTTP
  hooks sample (`.claude/settings.local.json.example`)
- New baseline rules: `agents/no-pinned-model` / `ci/no-remote-test-workflows`
  (both start as warn)

### Changed

- **B: CI/CD policy change**: day-to-day CI moves to local Docker (`make ci`), and GitHub
  Actions is reduced to deploy on main push only. CI result JSON is written to
  `.guardsmith/ci-results/` as the interface for external tools. GuardSmith itself keeps
  an External PR CI limited to fork PRs
- **E: model/effort policy for agents**: qa uses fable / effort high, implementation
  agents default to sonnet (docs/AGENTS.md). Hardcoded date-suffixed model IDs are warned
  by the baseline (`agents/no-pinned-model`)
- Bumped remote-reference tags and generated-artifact stamps to v0.5.0 (baseline drift
  source / policy generated by `guard new` / docs examples)
- npm: `@guardsmith/core` 0.3.0 / `@guardsmith/cli` 0.3.0 (the Action's `cli-version`
  default is also 0.3.0)

## v0.4.0 (2026-08-14)

### Added

- **Single-bundle distribution via GitHub Releases**: a `guard.mjs` with all dependencies
  bundled, plus a presets/standards tar.gz, attached to each release. Environments that
  cannot reach the npm registry (air-gapped networks, egress restrictions) can use the CLI
  from GitHub alone (`node guard.mjs lint`)
- **Source selection for the Action**: new `source: npm | release` input (default npm).
  `release` uses the GitHub Releases bundle and runs without the npm registry
  (pin the tag with `release-tag`)
- Bundled bilingual (en/ja) READMEs in the npm packages (`@guardsmith/core` /
  `@guardsmith/cli` 0.2.2 — fixes the missing package description on npmjs.com)

### Changed

- Decoupled `guard new`'s reference tag from the npm version (`STANDARDS_TAG`). The
  reference tag is now bumped only in releases where the standards content changed
  (currently v0.2.1)
